# MASTER DEVELOPMENT PROMPT: AUTOCHIP FINDER

## Professional Android PDF Search & Automotive Chip Database Application

**Act as a senior Android developer, UI/UX designer, software architect, and mobile application performance engineer.**

Build a complete, production-quality Android application named **AutoChip Finder**. This application is designed for automotive technicians and electronics professionals who use **CG100X and iProg Pro** tools and need to search large PDF databases quickly by part number, chip number, and other relevant information.

The application must have a modern, premium, visually attractive interface with smooth animations, excellent performance, a simple user experience, and a fully dynamic PDF management system.

**Important:** Do not create just a static UI prototype. Build a fully functional application with real PDF import, indexing, searching, PDF viewing, persistent storage, and working navigation.

# 7. Advanced Search Engine

This is the most important part of the application.

Develop a fast and reliable local PDF search engine.

### A. Part Number Search

Allow users to enter part numbers such as:

* 13503645
* 77960-TF0-H420-M3
* 9012526

Search the indexed content of the PDFs assigned to the selected module.

Support:

* Exact matching.
* Case-insensitive matching.
* Partial matching.
* Flexible handling of hyphens and spaces.
* Fast results while typing.
* Search history.
* Clear search button.

Do not automatically remove meaningful characters from the displayed results. Normalization should be used for matching while preserving the original text.

### B. Chip Number Search

Allow searches such as:

* 95080
* 95160
* SPC560P50L3
* R7F701A033
* 93C86

Search for the requested chip number across the relevant indexed documents.

The search engine must handle both numeric and alphanumeric chip identifiers.

### C. Search Results

Display the results in modern, readable cards.

Each result should include, when available:

* Part number.
* Chip number.
* Brand or manufacturer.
* Vehicle or module information.
* Matching text snippet.
* PDF filename.
* Page number.
* Search match type.

The displayed fields must be extracted from the actual PDF content. Do not fabricate missing information.

**Result interactions:**

* Tap a result to open the corresponding PDF at the matching page.
* Highlight the matching term in the PDF viewer wherever technically possible.
* Allow the user to copy part numbers and chip numbers.
* Provide a share action for copying or sharing useful result details.
* Allow users to bookmark important results.

If the PDF has no structured records or its text cannot be reliably parsed into fields, show the matching text and page reference instead of forcing an incorrect table structure.

### D. Search Performance

Optimize the search engine for large PDF collections.

Requirements:

* Extract PDF text once during import.
* Store extracted text and searchable metadata in a local database.
* Use SQLite with appropriate indexes or a suitable local full-text search mechanism.
* Perform searches without reopening and parsing every PDF from scratch.
* Use background processing for large document imports.
* Implement debouncing for live search.
* Paginate large result sets.
* Keep the interface responsive while indexing or searching.
* Handle documents containing thousands of records.

The search engine should support searches across all imported PDFs in a selected module and optionally across all modules of the selected tool.

## Additional Feature: Global Smart Search (Unified Search Across All PDFs)

Integrate a powerful **Global Smart Search** feature into the AutoChip Finder Android application. This feature should work alongside the existing CG100X and iProg Pro sections without replacing or disrupting their individual search functionality.

### 1. Global Search on the Home Screen

* Add a prominent, modern search bar on the home screen, preferably below the app title and above the CG100X and iProg Pro buttons.
* Use a clean search icon, rounded corners, subtle animations, and a professional design.
* Allow users to search for a part number, chip number, module name, brand, or other relevant text.
* Include a clear button and a search history option.
* Search across all imported and indexed PDFs from both CG100X and iProg Pro.

### 2. Smart Search Results

When a user enters a search query, display matching results from all available PDF files in a well-organized layout.

Each result should show:

* **Tool:** CG100X or iProg Pro.
* **Module:** For example, Airbag, BCM, ECU, Dashboard, or another configured category.
* **PDF file name:** The original document where the match was found.
* **Matched part number or chip number:** Highlight the matching text.
* **Brand or vehicle information:** If available in the source PDF.
* **Page number:** The exact page containing the match.
* **Short context or preview:** A small excerpt around the matched text.

Make each result clickable. When tapped, open the corresponding PDF at the exact page containing the match and highlight the matching text where technically possible.

### 3. Advanced Search Filters

Add optional filters to help users narrow down their results:

* **Tool:** All, CG100X, or iProg Pro.
* **Module:** All modules or a specific module.
* **Search type:** Part number, chip number, brand, module, or all text.
* **PDF file:** Search within a particular imported document.

Filters should be easy to use and should not make the interface complicated.

### 4. Intelligent Matching

Implement a practical search engine that supports:

* Exact matching for part numbers and chip numbers.
* Partial matching when a user enters only part of a number.
* Case-insensitive text search.
* Handling of common spaces, hyphens, and formatting differences in part numbers.
* Suggestions for similar matches when no exact result is found.
* Fast results while the user types, with a small debounce to avoid unnecessary processing.

Do not alter the original part numbers or chip numbers displayed from the PDF. Any normalized value should be used only internally for matching.

### 5. Search History and Favorites

* Save recent search queries locally.
* Allow users to clear individual search history entries or the entire history.
* Allow users to bookmark important search results.
* Provide a dedicated favorites section for quickly accessing saved results.
* Keep all history and favorites stored locally on the device.

### 6. Search Index and Performance

* Build a searchable local index when PDFs are imported or updated.
* Extract text and relevant information from PDFs without repeatedly processing the entire document for every search.
* Keep the index synchronized when PDFs are added, replaced, renamed, or deleted.
* Support large PDF files and avoid blocking the main UI thread.
* Display a clear indexing progress indicator when processing a new document.
* If a PDF contains scanned images rather than selectable text, clearly indicate that text extraction may require OCR. Do not silently claim that such a document has been fully indexed if it has not.
* Make the search engine work offline without requiring an internet connection.

### 7. Search Experience and UI

* Create a dedicated global search results screen with a clean, modern layout.
* Group results by tool or module when appropriate.
* Provide loading, empty, no-results, and error states.
* Use subtle animations when results appear and when filters are changed.
* Make matching numbers visually prominent and easy to copy.
* Ensure the screen works smoothly on different Android screen sizes.
* Support both light and dark themes.

### 8. Technical Integration

* Integrate global search with the existing PDF import system, module management, local database, and PDF viewer.
* Reuse the same indexing and search logic for the individual CG100X and iProg Pro sections wherever possible.
* Store each indexed record with its source PDF, tool, module, page number, extracted text, and relevant metadata.
* Use a scalable architecture so that future tools, modules, and PDF collections can be included without redesigning the search system.
* Keep the application local-first and avoid unnecessary external APIs or cloud services.

### 9. Important Behavior

* Global search must include only PDFs that have actually been imported and indexed.
* Never generate fake part numbers, chip numbers, brands, or search results.
* If the same number appears in multiple PDFs, show all relevant matches with their respective source documents and page numbers.
* If a search returns no results, suggest checking the spelling or trying a shorter query.
* Make it possible to open the original PDF directly from every search result.

### 10. Acceptance Tests

Before considering the feature complete, verify that:

* A part number found in a CG100X PDF can be located through global search.
* A chip number found in an iProg Pro PDF can be located through global search.
* A query can return results from both tools at the same time.
* Filters correctly restrict results by tool, module, and PDF.
* Tapping a result opens the correct document and page.
* Search still works after closing and reopening the application.
* Adding a new PDF makes its indexed content available to global search.
* Replacing or deleting a PDF does not leave stale search results.
* The feature remains responsive with a large collection of imported PDFs.

**Implementation instruction:** Integrate this feature into the main application architecture described in the first prompt. Do not build it as a separate app or a disconnected demo. First inspect the existing project structure and implement the feature in a way that preserves the original requirements, design, and functionality.
